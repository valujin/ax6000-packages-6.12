# AX6000 Mesh: controller Wi-Fi networks and guest isolation

## Intent and current limits

The controller's client networks must propagate to each agent, including separate guest networks and their VLAN isolation. Changes, additions and removals should converge automatically; client roaming and a preference for 5 GHz are goals, subject to client behavior and measured link quality. The existing generation supports exactly one LAN client AP and one dedicated backhaul AP per radio. Its saved WTS profile is not regenerated after a committed controller change, its agent persister is limited to two slots, and its VLAN-disabled bridge cannot implement guest isolation. Both the existing r5 generation and these proposed changes require two-node validation.

## Policy and stable mapping

The controller is authoritative for logical network definitions. Each network has a persistent, locally collision-checked VLAN ID from 1–4094; the management/primary network has one explicit primary VID and a PCP in 0–7. Existing configured VLAN IDs and trunk allocations must be preserved; never allocate by silently reusing a VID. The same logical network uses the same VID on both bands and all agents. Multiple SSIDs may use the same network and VID; a single SSID cannot identify different logical networks or VIDs because MAP R2 traffic separation maps SSID to VID. If a same-named SSID appears on both bands, network, VID, security and isolation must match; duplicate same-band SSIDs are rejected. Preserve band-specific credentials, hidden state, and other properties only where a verified vendor representation exists. Unsupported enterprise/security modes, non-transportable policies or configurations exceeding measured limits must be reported specifically and leave the last known safe configuration in place; do not silently omit or flatten a guest network into LAN.

For each radio, reserve AP index 1 (`ra1`/`rax1`) for the existing dedicated backhaul; client BSS slots are assigned deterministically in controller order to index 0, then 2, 3, etc. An agent must allocate and advertise enough actual slots before renewal: vendor `_1905_lib_io.c` caps M2s to the number of agent-reported BSSs. Controller WTS rows must follow the same priority mapping for 2.4 GHz and 5 GHz; 5GL/5GH rows are generated consistently. The planner takes explicit per-band AP capacity including the reserved backhaul slot, and rejects overflow. Schema and 1905 constants of 16 are upper bounds, not demonstrated hardware capacity. Slots must be revalidated on each node; enforce the smallest confirmed capability before accepting an update. Stable slot IDs and tombstones are needed across deletions and reordering to avoid renumbering a live BSS; initial planner slot ordering is only a proposed layout and must not be used as a persistent allocator without that layer.

The backhaul credentials remain separate from user SSIDs. Current stack uses hidden WPA2-PSK backhaul; WPA3 backhaul is a separate capability requiring a verified driver/WSC contract and actual interoperability tests, not a change of label.

## MAP R2 and data path

Build WTS entries from the validated controller state, carrying each client SSID's VID and the primary VID/PCP through the SDK's R2 policy format. `file_io.c` parses VID after hidden marker and optional `pvid`/PCP marker; the 1905 layer produces default 802.1Q and traffic-separation policies, and WAPP applies `ts_fh_vid`, `ts_bh_primary_vid`, `ts_bh_primary_pcp`, and `ts_bh_vid`. `mapTSEnable` flips a chip-wide traffic-separation flag and must be activated only when the complete policy and data path are ready. The 1905 DSA Ethernet traffic-separation callback currently returns success without installing VLANs; do not use that return as proof of wired isolation. Use an explicitly managed netifd/Linux bridge VLAN design or implement checked DSA operations, and verify actual resulting membership.

The controller remains the gateway and owns DHCP, IPv6 and firewall policies for every network. Each agent remains an L2 extension and must preserve unrelated firewall and WAN settings. A proposed transport is tagged primary and guest VLANs on dedicated wired or wireless backhaul, with only the primary management VLAN presented to the agent's DHCP client and each local FH BSS attached to its matching VLAN. The wireless driver may tag FH ingress itself: establish actual packet presentation before selecting bridge PVID and egress rules, so ingress is neither double-tagged nor accidentally classified as primary. Guest APs and trunk membership must remain blocked by default until the matching VLAN, BSS and policy have all been verified. A reboot, missing policy, partial update, unknown SSID, or unavailable agent must never attach guest traffic to the primary LAN. MAP R2's SSID→VID policy alone does not synchronize firewall, access-control or per-BSS client-isolation behavior; add a separately authenticated, versioned mechanism or reject configurations whose semantics cannot be carried. Do not claim full guest synchronization until those properties are verified end to end.

## Lifecycle and recovery

Stage a complete validated plan and WTS profile in a root-only location, with secrets never sent through arguments or status/log output. Atomically publish only after all slot and VLAN changes are locally safe, then invoke the vendor `mapd_cli /tmp/mapd_ctrl renew` path. A successful CLI return is not an agent acknowledgment. Track per-agent desired/applied generation and errors; retry agents that were offline and show partial convergence. Verify remote BSS/VID and dataplane state before reporting success. The controller's existing Wi-Fi reload hook must detect changes rather than merely preserve a committed WTS profile; coalesce updates under the Mesh/radio locks without holding the radio lock across `wifi up`. Update expected-owned configuration deliberately so disable does not erase user edits, retain the independent snapshot/watchdog, and perform the established driver quiesce/restore ordering when topology changes. Failed changes retain the previous safe VLAN policy and a recoverable transaction; do not roll back unrelated user changes.

The isolated planner is a pure, read-only decision component. It receives normalized JSON containing the primary network/VID/PCP, measured per-band AP capacities and client BSS records (identity, SSID, band, logical network, VID, security and isolation). It emits a deterministic proposed BSS/VID mapping or a specific validation error. It never allocates VLAN IDs, creates interfaces, reads UCI, runs network commands or receives Wi-Fi keys. Runtime owns stable allocation, credential custody, safe configuration changes and policy delivery. Planner output is not authorization to modify a live network.

## Steering and test plan

Use vendor centralized steering and 802.11k/v only where capability and configuration are proven. Prefer 5 GHz only for matching SSID, credentials and security with adequate measured signal and load; preserve 2.4 GHz fallback and avoid aggressive disconnects. `NetworkOptPrefer5Gover2G` is a backhaul optimization flag, not a client steering control. Current preflight rejects 802.11r; add FT only after a separately validated key/mobility-domain design. A client chooses whether and when to roam.

Automated tests must cover planner duplicate SSIDs, cross-band mismatch, VID collisions, reserved/out-of-range VIDs, capacity including the BH slot, multiple SSIDs on one network, malformed data and stable deterministic output. Integration tests must cover WTS escaping and per-band ordering, R2 policy encoding, slot exhaustion, hot reload, offline/rejoining agents, two agents, delete/re-add, generation conflict, partially applied or interrupted updates, restore and reboot, no key leakage, and no guest-to-primary bridge exposure.

Before enabling production guest sync, capture on actual controller and agent: wired dedicated-WAN and wireless BH tagged/untagged frames for primary and each guest VID in both directions; bridge VLAN tables and AP port flags; DHCP/IPv4/IPv6 and DNS reachability; denial of guest→LAN and guest→guest where required; guest internet policy; cross-node client movement; power-loss and partial-failure restoration; HNAT on/off; and client coexistence for 2.4-only, 5-only, dual-band, WPA2 and mixed mode. Repeat with VLAN conflict, missing/unsupported agent, and offline rejoin. No positive two-node guest or roaming result can be inferred from mocks or daemon health.
