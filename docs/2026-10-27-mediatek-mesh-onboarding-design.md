# AX6000 Mesh onboarding design (draft)

## Outcome and scope

A main router enables MediaTek EasyMesh using its existing client Wi-Fi. An additional AX6000 chooses Ethernet or Wi-Fi and joins without manually configuring its address, DHCP, or client Wi-Fi. Client Wi-Fi must support WPA2/WPA3 mixed mode, with a separate mesh backhaul. Existing non-mesh Wi-Fi must continue to work when mesh is disabled. Only the documented AX6000 topology is initially supported; reject other layouts before changing anything and explain the offending condition.

The baseline implementation in `ax6000-mesh-control` restricts APs to `psk2`, uses one SSID for both fronthaul and backhaul (`map_bss_type=96`, WTS FH/BH fields `1 1`), requires agent DHCP and IP setup beforehand, and snapshots wireless only. The baseline `status` reports daemon health, not joined peers. These are explicit gaps, not evidence of a working onboarding flow.

## Approach and decisions

Use the existing MediaTek EasyMesh stack, procd operation job and restricted RPC, extending them with a persistent transaction and observable enrollment state. Ethernet connects the agent WAN port to a controller LAN port; Wi-Fi uses a bounded, user-triggered vendor enrollment window on the controller, followed by automatic PBC when the agent starts joining, with no automatic open-ended scanning. Alternatives considered: requiring the user to preconfigure IP/DHCP fails the requested flow; replacing the vendor stack with 802.11s changes the product and does not establish EasyMesh interoperability. The SDK sample uses separate BH-only (`1 0`) and FH-only (`0 1`) WTS profiles, and client auth `0x0060` (WPA2-PSK plus SAE), encryption `0x0008` (AES); the UCI mixed mode is `sae-mixed`. Additional BSS slots and the correct role-specific enrollment still need implementation and hardware verification. Vendor event/status interfaces must be confirmed from the actual SDK and tested before coding: do not infer separate backhaul, mixed-mode support, WPS success, or topology merely from accepted configuration or running processes.

The controller keeps its LAN and DHCP configuration. The agent changes LAN to DHCP client and disables every LAN DHCPv4 server, IPv6 RA, DHCPv6, and NDP relay as one recoverable transition. Preserve WAN, firewall and unrelated UCI settings. Reject pending changes in every affected package and unsupported or ambiguous layouts before any mutation. Do not overwrite existing user changes silently on disable.

## Transaction and recovery

1. Serialize all configure/apply/pair/disable/recovery operations with the same lock. Validate the configuration, executable dependencies, vendor mode, and available persistent storage first. Snapshot original `/etc/config/network`, `/etc/config/dhcp`, `/etc/config/wireless`, relevant radio profiles, and mesh settings, including absent-file markers and permission metadata, in a root-only persistent directory. Include any other file actually mutated by the selected implementation. Prepare a complete manifest and checksums; atomically publish a durable `prepared` marker only after the snapshot is complete and flushed. Never remove the only valid snapshot on a failed restore.
2. Before network mutation, arm a persistent rollback watchdog with a 360-second onboarding deadline and mark the transaction pending. Restoration runs afterward and can take additional time, including up to 270 seconds for the bounded radio restore callback. Apply changes in an order that never bridges an active agent DHCP/RA server to the main LAN: stop LAN DHCP/RA and verify it stopped before bridging the agent WAN or wireless backhaul. Configure the LAN DHCP client and mesh-owned wireless settings; reload services and start mesh. Report operation stage and actual bounded errors, excluding passwords and sensitive daemon output.
3. Commit the transition only after the agent has a usable DHCP lease and independent, verified evidence that it joined the intended controller over the selected backhaul. A daemon ping, a local link, or a lease by itself is not proof of enrollment. Pairing is bounded and failure, missing lease, wrong uplink, watchdog expiration, cancellation, daemon failure, or interruption causes rollback. The controller shows the agent's management address only when a verified mapping from peer identity to DHCP lease/address is available; otherwise say the address is unknown. Do not display a guessed address.
4. On reboot while pending, restore the entire original snapshot before starting mesh or applying network configuration, including DHCP/RA service state, then persist a failure message for the next UI session. Remove the agent WAN port from the LAN bridge before restoring its original LAN address and DHCP server. Recovery must work without an existing browser session, sane wall clock, or a running RPC daemon. Test ordering on real init dependencies. A committed mesh survives reboot and temporary link loss; recovery timers for setup must not repeatedly undo a previously successful installation.
5. Disable uses the saved snapshot to restore the full original settings. Detect conflicts in all owned configuration before restore and present a concrete recovery path instead of silently clobbering edits. For any partial restoration failure, retain the snapshot and persistent error and allow retry. Where old settings may have the same address or DHCP server as the main router, explicitly disconnect the agent backhaul before restoring them. Provide a physical/local recovery route in the user documentation.

A move to DHCP can change the agent's management URL and interrupt the current browser. The setup screen must explain this before starting, show progress while reachable, and direct the user to the main router's topology view for the new address. Rollback returns the original local management settings if enrollment times out. The implementation must not claim that the controller can link to the agent until its address mapping is supported by actual data.

## UX and observability

Offer role selection and Enable on the main router; on the additional node offer Ethernet/Wi-Fi and Join. Show phase-specific statuses: preparing, awaiting connection/pairing, obtaining address, validating peer, connected, and restored after failure. Pairing must expose a real timeout and actual rejection/failure when available; otherwise indicate that the result is unknown rather than spinning forever. The main router shows known agent identity, link type, state and address only when each is available and confirmed. Keep service health separate from enrollment. On a disconnected page, show reconnection instructions; do not pretend a network error proves either success or rollback.

Separately generated backhaul credentials must be secret, persisted with root-only access, stable across reboot, and transmitted only by the supported vendor enrollment mechanism. Verify mixed WPA2/WPA3 client mode, AP/BSS capabilities, separate BSS flags, actual PBC entry points for both roles, and topology query formats against the exact SDK; fail closed if any necessary capability is unverified. Avoid logging credentials. Preserve the normal mesh-off configuration and support explicit recovery of secrets-bearing snapshots through sysupgrade.

## Code ownership and verification

- `ax6000-mesh-control`, operation job/init and a boot recovery helper own preflight, snapshots, mutation order, watchdog, rollback, and secret handling. Adjust sysupgrade preservation as necessary.
- RPC owns bounded, structured stage/error/peer reporting and fixed enumerated operations; ACLs remain least privilege. The LuCI view owns role-specific steps, management handoff, progress, topology and actionable failure/recovery messages. Update translations and `docs/MEDIATEK-MESH.md` to match the implemented behavior.
- Extend runtime tests with isolated fake UCI, init and vendor commands for successful transitions, per-step failure, timeout, process kill, reboot at each durable stage, restoration retry, pending edits, DHCP/RA shutdown ordering, and conflicting user edits. Verify mixed encryption and separate BH using actual vendor configuration contracts; check no secrets leak into status or logs. Test RPC authorization, status semantics, UI progress and management URL handling. Run shell syntax, targeted Python tests and package/image integration checks.
- Two physical AX6000 devices are required to verify wired and wireless enrollment, mixed-mode clients, separate backhaul, DHCP/IPv6 behavior, peer address reporting, reboot/link recovery, roaming and rollback on actual interruption. A one-device service check or passing mocked test does not establish these outcomes. Until these tests and vendor contracts pass, mark the feature experimental and report the unverified behavior accurately.
