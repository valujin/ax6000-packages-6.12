# План отдельных сборок 6.12 и сохранения каналов

Проект подготовлен 12 октября 2026 года. Линия 6.6 завершена в отдельном репозитории; обе линии 6.12 опубликованы в этом репозитории. Фактические результаты публикации приведены в README; этот документ сохраняет архитектурные решения и порядок проверки. Исходный checkout и работающие сервисы сервера не изменяются.

## Порядок и изоляция

Сначала завершить текущую сборку Linux 6.6: прошивка stock, соответствующий SDK, все совместимые выбранные kmods и проверенная подписанная публикация. Затем создать отдельный git-репозиторий `/home/valuxin/dev/owrt/ax6000-packages-6.12`, сохранив 6.6 как самостоятельную линию. Скопировать исправленные инструменты из явно зафиксированного commit; не использовать текущий рабочий каталог 6.6 для экспериментальной конфигурации.

Два канала 6.12:

| Канал | Зафиксированный source commit | Ядро | Статус |
|---|---|---|---|
| `recommended` | `ae65e1de69971b5a2e3cf7e39390ee93f274d488` | 6.12.108 | Кандидат до проблемного merge; stock ещё требует проверки на роутере |
| `latest` | `a99b0888b88f134f56bcb2a7d93027b5d20638a9` | 6.12.112 | Зафиксированный исследованный snapshot; известные отчёты о регрессии HNAT |

Оба commit относятся к [chasey-dev/immortalwrt-mt798x-rebase](https://github.com/chasey-dev/immortalwrt-mt798x-rebase). Обоснование и ограничения испытаний приведены в [KERNEL-6.12.md](KERNEL-6.12.md). Название `latest` означает этот явно выбранный snapshot, а не автоматическое переключение ядра на изменяемый HEAD.

Порядок полной компиляции: одна multi-profile сборка `recommended` для трёх AX6000 layouts, затем такая же сборка `latest`. Всего две полные сборки, а не шесть независимых сборок по layout. Каждому каналу нужны собственные source/work/output, профиль, lock и resume fingerprint. Внутри канала ядро, пакеты и экспортируемый SDK общие; совпадение фактического ABI трёх образов подтверждается после сборки. Общий `dl` допустим; подготовленный kernel tree, staging target и готовые IPK разных каналов/поколений смешивать нельзя. Общий build-lock должен охватывать оба репозитория; одновременно работает одна тяжёлая сборка, в прежнем лимите 4 CPU и 10 GiB RAM. Компилировать сразу stock/mtkuboot/ubootmod, но первым испытывать stock на текущем роутере. Обоснование правил и точные symbols приведены в [MULTILAYOUT-6.12.md](MULTILAYOUT-6.12.md).

**Linux 6.18 отложен по явному решению пользователя до появления полного vendor-порта для MT7986/AX6000.** Репозиторий, профиль и сборку 6.18 сейчас не создавать. Наличие official OpenWrt 6.18 с mt76 не выполняет это условие; исследование и пробелы доказательств приведены в [KERNEL-6.18.md](KERNEL-6.18.md).

## Исторический план builder и последующие изменения

Пункты ниже сохраняют исходный OPKG/IPK-план. Текущий опубликованный recommended
уже использует APK; опубликованный latest по-прежнему OPKG (снимок `074e68e5…19ea3`).
Не применять историческое отключение USE_APK к принятому recommended APK-поколению.
Tailscale r2/static в этом плане также исторический: реальная SDK-сборка r3
использует upstream source-multicall/UPX, один ELF и две ссылки, без Go backport
в SDK. APK — 11 921 395 байт, Installed-Size 12 225 198 байт. Подписанный
REC Release `bcdea080…3b4ed` опубликован, активация 39711729943 и свежая HTTPS-проверка
изменённых файлов успешны; неизменённые файлы наследуют прежние полные проверки.
Обычный ROM не включает Tailscale; ASU сохраняет его только если он уже установлен.
[Текущие факты и ограничения](tailscale-sdk-acceptance.md).

1. **Формат пакетов.** В 25.12 `USE_APK` имеет default `y`. Source configure/select и SDK select должны явно записывать `# CONFIG_USE_APK is not set`, включать `CONFIG_PACKAGE_opkg=y` для образа, сохранять `CONFIG_SIGNED_PACKAGES=y` и `CONFIG_SIGNATURE_CHECK=y` в прошивке. После `defconfig` проверить эти значения и отсутствие выбранного APK package manager. После сборки проверять IPK-выход и manifest образа; выполнить отдельную проверку LuCI package manager с opkg. SDK может отключать собственное индексное подписание: итоговый feed по-прежнему подписывает publisher. Первичные источники: [Kconfig](https://github.com/chasey-dev/immortalwrt-mt798x-rebase/blob/ae65e1de69971b5a2e3cf7e39390ee93f274d488/config/Config-build.in), [opkg](https://github.com/chasey-dev/immortalwrt-mt798x-rebase/blob/ae65e1de69971b5a2e3cf7e39390ee93f274d488/package/system/opkg/Makefile), [выбор IPK/APK](https://github.com/chasey-dev/immortalwrt-mt798x-rebase/blob/ae65e1de69971b5a2e3cf7e39390ee93f274d488/include/package-pack.mk).

2. **Vendor baseline.** Начать с нового `defconfig/mt7986-ax6000.config`, не переносить целиком `.config` 6.6. Он уже использует `mediatek/filogic`, но выбирает множество устройств — оставить ровно три AX6000 layouts через MULTI_PROFILE и PER_DEVICE_ROOTFS, установленные до defconfig. Использовать `CONFIG_TARGET_DEVICE_mediatek_filogic_DEVICE_xiaomi_redmi-router-ax6000-{stock,mtkuboot,ubootmod}=y`, отключить ALL_PROFILES и все прочие device symbols; single-profile selection не оставлять. Сохранить глобально в каждом образе vendor `kmod-mt_wifi`, `kmod-conninfra`, `kmod-warp`, `kmod-mediatek_hnat`, настройки MT7986/MT7976, `AX6000` SKU, driver 7.6.7.3 и firmware `mt7986-fw-20260601`. Глобально выбрать `kmod-leds-ws2812b=y`, поскольку mtkuboot не добавляет его в DEVICE_PACKAGES. Два исследованных commit имеют одинаковые проверенные vendor defconfig и Makefile драйвера. [Defconfig](https://github.com/chasey-dev/immortalwrt-mt798x-rebase/blob/ae65e1de69971b5a2e3cf7e39390ee93f274d488/defconfig/mt7986-ax6000.config), [multi-profile детали](MULTILAYOUT-6.12.md).

3. **Управление Wi-Fi.** Сохранить `mtwifi-cfg-ucode`, `ucode-mod-datconf`, `ucode-mod-l1parser`, `iwinfo-ucode`, `ucode-mod-iwinfo`, `wifi-dats`, vendor utilities и LuCI `luci-app-mtwifi-cfg`. `mtwifi-cfg-ucode` конфликтует с прежним `mtwifi-cfg`; `iwinfo-ucode` требует отсутствия выбранного `iwinfo`. Для ALL_KMODS отдельно проверить итоговый `WIFI_SCRIPTS_UCODE`: cfg80211 выбирает прежний iwinfo только при `!WIFI_SCRIPTS_UCODE`. Нельзя потерять рабочее управление vendor Wi-Fi ради выбора необязательного kmod. [mtwifi-cfg-ucode](https://github.com/chasey-dev/immortalwrt-mt798x-rebase/blob/ae65e1de69971b5a2e3cf7e39390ee93f274d488/package/mtk/applications/mtwifi-cfg-ucode/Makefile), [iwinfo-ucode](https://github.com/chasey-dev/immortalwrt-mt798x-rebase/blob/ae65e1de69971b5a2e3cf7e39390ee93f274d488/package/network/utils/iwinfo-ucode/Makefile), [cfg80211](https://github.com/chasey-dev/immortalwrt-mt798x-rebase/blob/ae65e1de69971b5a2e3cf7e39390ee93f274d488/package/kernel/mac80211/Makefile).

4. **Feeds.** Packages/LuCI/routing/telephony используют `openwrt-25.12`, а новый vendor feed list содержит также `video`. Полные актуальные SHA всех пяти feeds и внешнего AWG закреплены в [FEEDS-6.12.md](FEEDS-6.12.md); использовать согласованный набор внутри каждого канала, video оставить для широкой совместимой выборки, если его пакеты входят в metadata. AWG — отдельный зафиксированный community feed. Старые pins 24.10 не переносить. Source build имеет base-пакеты внутри дерева. SDK base feed теперь формируется как `src-git --root=package base URL^COMMIT`: поддержать этот флаг в профиле/генераторе и проверять HEAD исходного clone, доступного через `feeds/base_root`. Остальные feeds обычные. [feeds.conf.default](https://github.com/chasey-dev/immortalwrt-mt798x-rebase/blob/ae65e1de69971b5a2e3cf7e39390ee93f274d488/feeds.conf.default), [SDK base feed](https://github.com/chasey-dev/immortalwrt-mt798x-rebase/blob/ae65e1de69971b5a2e3cf7e39390ee93f274d488/target/sdk/Makefile), [обработка root](https://github.com/chasey-dev/immortalwrt-mt798x-rebase/blob/ae65e1de69971b5a2e3cf7e39390ee93f274d488/scripts/feeds).

5. **SDK и ABI.** Формат kernel dependency остаётся `kernel (= VERSION~VERMAGIC-rRELEASE)`. Нельзя брать SDK или kmods 6.6. Подготовленный SDK 6.12 сохраняет `.config`, headers/scripts, Module.symvers, modules.builtin и `.ko`, но проверенный список также не содержит `.vermagic`, `.config.set`, modules.builtin.modinfo. Перенести существующее augmentation с проверкой byte-equality `.config`/Module.symvers и дополнением этих файлов. Для каждого из двух full builds заново обнаруживать ABI из kernel IPK, сверять его с manifest всех трёх образов, kmod Depends и экспортированным SDK. Только при совпадении использовать общий SDK/feed внутри канала; при расхождении остановить публикацию до выяснения причины. [kernel.mk](https://github.com/chasey-dev/immortalwrt-mt798x-rebase/blob/ae65e1de69971b5a2e3cf7e39390ee93f274d488/include/kernel.mk), [SDK](https://github.com/chasey-dev/immortalwrt-mt798x-rebase/blob/ae65e1de69971b5a2e3cf7e39390ee93f274d488/target/sdk/Makefile).

6. **Выбор пакетов.** Сохранить список VPN/Tailscale/AWG/WireGuard/PBR/mwan3/GeoIP и русского LuCI, проверяя реальные symbols 25.12 после `defconfig`; версии пакетов и названия зависят от новых feeds. В первоначальном плане Tailscale использовал официальные static ARM64 с проверенной SHA256; это сохранено для воспроизводимости r2. Текущий r3 source-multicall/UPX описан выше; его отдельный закреплённый Go toolchain не заменяет компилятор SDK. ALL_KMODS выбирает только совместимые с новым контекстом модули. Зафиксировать selected/incompatible report и сравнить выбранные имена с реально построенными IPK. AWG на 6.12 требует отдельной полной compile-проверки.

## Layout как часть идентичности

Все остальные device symbols должны быть выключены. Профиль полного build/lock/state описывает канал и весь набор devices; отдельная image identity описывает layout. SDK/feed общие внутри канала после фактической ABI-проверки, а не три независимых профиля SDK. Выбор image на сайте должен сопоставлять `board_name` и layout; одна проверка архитектуры и ABI для выбора прошивки недостаточна.

## Сохранение пакетов полного build

Проверка реального `.packageinfo` и `.config` текущей 6.6 показала 1035 выбранных kmods. Замораживания одних модулей недостаточно: например, r8169 требует r8169-firmware, crypto-hw-safexcel — eip197-mini-firmware, cfg80211 — iw/iwinfo/wifi-scripts/wireless-regdb, batman-adv — виртуальный batctl (выбран batctl-default). Provider-aware metadata closure обнаружила 63 выбранных non-kmod имени вне dependency closure ежедневного списка. Некоторые уже входят в firmware; остальные должны оставаться в feed для установки необязательных модулей.

Для post-build export 6.6 уже добавлена реализация по **окончательным IPK control Depends/Provides**: сохранить все успешно собранные пакеты вне списка явно обновляемых, включая frozen kmods, vendor GUI/tools, переводы и транзитивные userspace/firmware зависимости. Проверка зависимостей учитывает built virtual providers и альтернативы. Manifest содержит allowlist `frozen_packages`; `frozen_kmods` остаётся отдельным списком. Явно обновляемые requested external/userland пакеты не замораживаются; вновь построенные зависимости заменяют сохранённые копии по Package. Непредоставленная runtime dependency приводит к отказу export с указанием ребра. Publisher по-прежнему исключает kernel/libc/base-files/busybox/opkg из supplemental feed. Регрессия проверяет сохранение полного множества предлагаемых имён пакетов при ежедневном обновлении, цепочку module → firmware → library → libc, виртуальный provider, versioned alternative и ежедневную замену свежей библиотеки/AWG. То же поведение перенести в 6.12 после проверки реального SDK.

## Публикация всех каналов

Идентификатор build-профиля содержит kernel-line и канал, например `redmi-ax6000-612-recommended`; layout хранится в отдельных image records. В sibling repository публикация имеет два независимых префикса **`channels/recommended/` и `channels/latest/`**. В каждом размещать один `profile.json`, `repository.pub`, `state/lock.json`, подписанный общий feed и ссылку на один immutable SDK. Образы показывать как отдельные downloads stock/mtkuboot/ubootmod, например `channels/recommended/downloads/stock/` и соответствующие layout directories; исходные immutable assets могут находиться в GitHub Release. Каждый download record содержит device/layout, filename, checksum и результат проверки; это не отдельный package feed.

Текущий installer поддерживает `PACKAGE_REPOSITORY_URL` — направлять его на префикс канала без layout; проверка совпадения реальных ABI/архитектуры сохраняется. Все три layouts одного проверенного поколения используют этот feed. Один настроенный custom feed не переключать на другой канал молча. Сайт должен давать отдельный явно подписанный выбор image/layout, первым для текущего пользователя — stock.

`build_id` теперь должен включать digest готового augmented SDK: `id-sourcecommit12-sdksha12`. Это различает полные поколения с одинаковым source commit, но иными feeds/kernel configuration/набором devices. Одно поколение канала включает все три image identities и общий SDK; изменение набора layouts требует повторной проверки конфигурации/ABI и согласованного перевыпуска assets, а не произвольного добавления файлов к прежнему SDK. URL уже опубликованного SDK не менять и не заменять другими байтами. Daily source locks обновляются отдельно от полного firmware generation: изменение source/kernel должно создавать новое поколение firmware+SDK, а не запускать package-only build с новым ядром.

Каждый daily workflow строит только изменившиеся tracks, но deployment содержит **все** опубликованные tracks. Рекомендуемый алгоритм: один сериализованный publish job восстанавливает проверенные durable snapshots всех каналов, заменяет только успешно построенные channel subtrees, проверяет подписи/SDK URLs/manifest/lock каждого канала и атомарно деплоит собранный общий сайт. Непубликовавшиеся channels не создавать как пустые feeds; ошибки/неизменившиеся locks сохраняют последний успешный subtree. Не полагаться на истекающие Actions artifacts как единственное постоянное хранилище; сохранять release snapshot/manifest с digest для восстановления. Неизменённые subtree должны оставаться byte-identical. Между channel publish jobs общий concurrency group, отдельные namespaced artifact names.

SDK и образы целесообразно хранить в immutable GitHub Releases каждого `build_id`, а Pages использовать для каталога и подписанных feeds; фактический SDK URL профиля может вести прямо к release asset. Опубликованный Pages сайт ограничен 1 GB, каждый release asset — менее 2 GiB. До загрузки проверять суммарный объём и отдельные размеры; для большого SDK потребуется уменьшение/раздельный kernel baseline с отдельной проверяемой SHA256, а не необъявленная смена URL. Источники: [Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits), [release limits](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

## Проверки при реализации

- После source defconfig: MULTI_PROFILE/PER_DEVICE_ROOTFS, ровно три разрешённых AX6000 devices и ALL_PROFILES выключен; opkg/IPK, подписи в прошивке, общая vendor driver/ucode chain и обязательные image packages сохранены. После SDK defconfig: согласованный экспортированный kernel context и IPK-формат.
- После каждого из двух world builds: правильные metadata/layout всех трёх образов, vendor manifest каждого образа без mt76 Wi-Fi driver packages, фактическое совпадение kernel identity, точные kernel Depends всех kmods, каждое выбранное имя построено, один SDK context совпадает. При несовпадении ABI общий feed не публиковать.
- На augmented SDK: compile AWG и запрошенного userspace, daily merge сохраняет frozen module dependency closure и assets, затем проверка усign над распакованным Packages.gz.
- В тесте публикации двух каналов: обновить один; второй profile/lock/feed/signature/SDK link должен сохраниться. Одинаковый source commit с иным SDK даёт другой build_id и URL. Старый URL остаётся доступным.
- Испытания на AX6000 stock — отдельный этап после компиляции: Ethernet, оба диапазона Wi-Fi, WPA2/WPA3, HNAT, VPN/PBR/multi-WAN, производительность и стабильность. Успешная компиляция или чужой mtkuboot release не доказывает успешную загрузку stock.
